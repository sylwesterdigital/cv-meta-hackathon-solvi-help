# SOLVI.help v0.2.212 — executable local construction and sustained patrol

## Evidence and causes
The observed Sakk/Hoe work orders were restored correctly, but `/api/robots/autonomy/plan` rejected requests because the server had no active Meta API key for those particular requests. The existing deterministic recovery policy recognised only narrow `house` singular instructions; it could select `ask`, `rest` and `idle` without performing construction. `wander` always ran approximately 2 m even if the user requested an hour, and "step back 15m, turn random angle" fell back to a fixed 90° turn. Conversation replies and ambient movement receipts are not construction work orders.

## Implementation

- New **Local project · build without Meta** work-order mode uses the existing authenticated and editor-authorised `build_house` / `build` scene tools. No Meta model request is made for this mode. An explicit user-authored `@all start building more homes` or `@all please build a picnic area` in shared chat may initiate up to **three** local work orders for robots the current user can edit, provided they are not already under a work order, manually controlled, or on an active route. This is a narrowly parsed positive instruction; open-ended creative conversation and robot replies do not create work orders.
- "Build more homes" yields a **maximum of two** verified furnished house projects per assigned robot. A picnic corner is at most a table, two chairs and a bottle. A basic park/playground *corner* is at most a table, two chairs and a stool; this is not claim of full recreational equipment or landscape design. All placements use existing collision-checked worksite planning, object ownership rules, editor creation methods, shared scene persistence and server object edit validation. Every outcome is evidenced by stable object IDs; the saved state is bounded and revalidated against current scene objects on resume.
- Meta-based **Agent** mode also falls back to these bounded, real tool steps while model planning is unavailable; local steps may continue after a 12-second bounded delay without repeating billable calls. Provider backoff remains intact. A local project automatically stops after its complete, checked milestones and does not idle or invent progress indefinitely. Active, separately authorised work orders are never overwritten by a new group instruction.
- Time-qualified wandering, e.g. `@Sakk wander for one hour`, starts a capped 60-minute **patrol** with successive collision-aware 4–16m legs, changing headings and keeping the same command until it stops or reaches its time bound. It never teleports, runs in a closed browser, or guarantees uninterrupted motion if the surrounding world is completely blocked. A failure to find a further safe leg is recorded as `blocked`, not `arrived`.
- The instruction `@all step back 15m, turn random angle and restart` now has its own **recover_route** mission: find a physically reachable retreat direction up to the requested distance, visibly turn by a genuinely random (not hardcoded 90°) angle, then navigate a checked 3–9m exploratory leg. A blocked route yields a reported failure/partial outcome, not teleportation. `@Robot turn random angle` also chooses a non-fixed, bounded angle and direction. Human STOP/ownership checks remain.

## Explicit non-goals and limits

- A browser tab with an authenticated, visible WebGL scene is required. Persistent SQLite work orders are not background worker processes; they resume only when the app is open, authorised, and has the necessary scene objects.
- v0.2.212 does not introduce autonomous flying, world-deformation, sophisticated multi-robot allocation, infinite chat loops, valid medical care, functional playground devices or unrestricted removal/pushing of arbitrary objects. Model-dependent visual reasoning still requires a valid Meta key (backend environment/config or the **same browser tab's** session key). Do not conflate a previous Meta conversation on another profile/tab with a configured key for Sakk/Hoe's planner.
- A scene edit can fail for geometry, ownership, profile permissions, insufficient space, client inactivity or network loss. No "success" is claimed until an authorised scene tool returns an object ID. A construction failure keeps the task marked incomplete.
- The client retains all prior v0.2.211 robot-motion interpolation and v0.2.210 fence navigation. No database schema migration, credential changes, original GLB/media changes or profile/scene resets.

## Manual acceptance checklist

1. With the same signed-in browser controlling a permitted robot, send `@all start building more homes for new robots`. Confirm up to three new bounded local project work orders appear, that existing active orders are preserved, and that new houses/floors/furniture are actually created and saved with stable IDs. Refresh after an item is placed and verify no duplicate earlier milestone is built.
2. Send a conversational `@all you are free to make a nicer realm with parks`. Confirm this alone does **not** authorise scene edits. Send `@all please build a picnic area` and confirm permitted robots create actual table/chairs/bottle within physical and ownership constraints.
3. Disable the Meta key in a test environment. Use Local project and verify deterministic construction continues without requests to `/api/robots/autonomy/plan`. Use a Meta Agent build-house work order and verify the first failed call enters provider backoff while local authorised building is attempted. Do not label the failed inference as a successful model decision.
4. Send `@Sakk wander around for 1 hour`; verify more than one leg is executed, paths are A*/collision-checked, opposite browser receives smooth walking as in v0.2.211, STOP halts the patrol and tab closure stops actual execution.
5. Send `@All step back 15m, turn random angle and restart`; verify a checked retreat, actual turn of varying angles and bounded onward leg; blocked geometry is not crossed and failure cannot be reported as arrival.
6. In a second browser/profile and after server reload, verify realm objects, robot positions, inventory/backpacks, GLBs and owners remain unchanged except for the specifically authorised new scene edits. Run the existing Mac watcher with backups; inspect the real Flask and two-browser results before declaring live deployment.
